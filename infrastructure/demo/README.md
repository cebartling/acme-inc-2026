# Runbook: AWS demo stack

The per-demo part of the AWS demo environment
([ADR-0064](../../documentation/adrs/0064-aws-demo-deployment.md)). You create it before a demo
and destroy it afterwards. It contains:

- a VPC in two Availability Zones, with public and private subnets and one NAT gateway;
- Amazon RDS for PostgreSQL, with logical replication on for Debezium, holding the five service
  databases: `acme_identity`, `acme_customers`, `acme_notifications`, `acme_products`, `acme_carts`;
- Amazon DocumentDB 8.0, with TLS on;
- Amazon ElastiCache for Redis, one node, with no TLS;
- Amazon MSK Provisioned: two `kafka.t3.small` brokers, topic auto-creation on, plaintext allowed;
- Secrets Manager secrets for the PostgreSQL and DocumentDB credentials;
- security groups: the data stores accept traffic only from one `services` group;
- an ECS cluster that runs the one-off task that sets up the databases, and the services:
  - the five backends (identity, customer, notification, product, shopping-cart) and the two
    frontends, one Fargate service each; identity runs two tasks, the rest one;
  - an ADOT collector that sends metrics to Managed Prometheus and traces to X-Ray;
  - CloudWatch log groups, one per service;
- one Application Load Balancer with an HTTPS listener: the frontends by host name, the backends
  by path on the API host (`alb.tf`);
- Route 53 records for `www.`, `admin.` and `api.<domain>`;
- per-deploy secrets, generated by Terraform: identity's JWT signing key, the test API key, and
  the service-to-service tokens.

The order service isn't deployed, so checkout doesn't work in the demo (ADR-0064, Open Decisions).

**Cost:** while it runs, roughly $350–500 a month at on-demand prices (ADR-0064, decision 7),
mostly MSK, DocumentDB and the NAT gateway. Destroy it after the demo.

Everything is destroyable: no deletion protection, no final snapshots, and secrets are deleted
with no recovery window.

## Prerequisites

1. **Foundation stack applied** ([`../foundation/README.md`](../foundation/README.md)). It owns the
   state bucket this stack uses.
2. **Tools:**
   - Terraform 1.17 (`terraform version`).
   - AWS CLI v2, signed in to the demo account with administrator rights
     ([`../aws-cli-sign-in.md`](../aws-cli-sign-in.md)). Check with `aws sts get-caller-identity`.
   - The CLI pointed at the stack's Region: `export AWS_REGION=us-east-2`.
   - `bash` on the machine that runs `apply`: a `local-exec` step starts the database setup task.
   - `jq`, for the manual check below.

Run the commands below from `infrastructure/demo`. From anywhere in the repository,
`just aws-demo <args>` runs `terraform <args>` in this directory.

## Create

### 1. Settings

Copy `terraform.tfvars.example` to `terraform.tfvars` and fill it in. `domain_name` must be the
domain the foundation stack was applied with. `email_from_address` must be a sender or domain
verified in SendGrid, or the verification emails won't arrive. The foundation stack's
SendGrid secret must hold the API key
([`../foundation/README.md`](../foundation/README.md)). With `sms_provider = "twilio"`, its Twilio
secret must be filled in too; the default, `mock`, sends no SMS.

### 2. Push the images

The services run the images in the foundation stack's ECR repositories, so push them before
`apply`. Until the deploy workflow exists (PIN-544), do it by hand. From the repository root:

```zsh
export AWS_REGION=us-east-2
registry="$(aws sts get-caller-identity --query Account --output text).dkr.ecr.$AWS_REGION.amazonaws.com"
aws ecr get-login-password | docker login --username AWS --password-stdin "$registry"

for service in identity customer notification product shopping-cart; do
  docker build -f backend-services/$service/Containerfile \
    -t "$registry/acme-$service-service:latest" backend-services/$service
  docker push "$registry/acme-$service-service:latest"
done

# The customer frontend has the API host baked in at build time, so build it with this domain.
api="https://api.<domain>"
docker build -f frontend-apps/customer/Containerfile \
  --build-arg VITE_IDENTITY_SERVICE_URL="$api" --build-arg VITE_CUSTOMER_SERVICE_URL="$api" \
  --build-arg VITE_PRODUCT_SERVICE_URL="$api" --build-arg VITE_INVENTORY_SERVICE_URL="$api" \
  --build-arg VITE_PRICING_SERVICE_URL="$api" --build-arg VITE_CART_SERVICE_URL="$api" \
  -t "$registry/acme-customer-frontend:latest" frontend-apps/customer
docker push "$registry/acme-customer-frontend:latest"

docker build -f frontend-apps/admin/Containerfile \
  -t "$registry/acme-admin-frontend:latest" frontend-apps/admin
docker push "$registry/acme-admin-frontend:latest"
```

Replace `<domain>` with the domain. Build for `linux/amd64`, which is what Fargate runs here:
on an Apple silicon Mac, add `--platform linux/amd64` to each `docker build`.

### 3. Apply

```zsh
terraform init -backend-config="bucket=acme-inc-2026-tfstate-$(aws sts get-caller-identity --query Account --output text)"
terraform apply
```

`apply` takes 20–30 minutes; MSK is the slow part. Before it creates the services it runs the
database setup task (`db-init.sh`) in the private subnets, which:

1. checks that RDS, DocumentDB, ElastiCache and MSK accept connections;
2. creates the five service databases in RDS if they don't exist.

If either step fails, `apply` fails. The task's output is in the CloudWatch log group
`/acme-demo/db-init`. Fix the cause and run `terraform apply` again.

If `apply` rejects an engine version, list what the Region accepts and set the matching variable
(`postgres_engine_version`, `documentdb_engine_version`, `kafka_version`) in `terraform.tfvars`.
Stay within PostgreSQL 16 (the parameter group family and the setup task image are 16) and a
ZooKeeper-mode Kafka 3.x version (`kafka.t3.small` can't run KRaft):

```zsh
aws rds describe-db-engine-versions --engine postgres --query 'DBEngineVersions[].EngineVersion'
aws docdb describe-db-engine-versions --engine docdb --query 'DBEngineVersions[].EngineVersion'
aws kafka list-kafka-versions --query 'KafkaVersions[].Version'
```

The services need DocumentDB 8.0.2 or later (retryable writes), and AWS applies a minor version
only when you choose it. After `apply`, check that the cluster runs 8.0.2 or later:

```zsh
aws docdb describe-db-clusters --db-cluster-identifier acme-demo --query 'DBClusters[0].EngineVersion'
```

## Check

Run the database setup task by hand. It is safe to repeat: it only creates what is missing.

```zsh
aws ecs run-task \
  --cluster "$(terraform output -raw ecs_cluster_name)" \
  --task-definition acme-demo-db-init \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[$(terraform output -json private_subnet_ids | jq -r 'join(",")')],securityGroups=[$(terraform output -raw services_security_group_id)],assignPublicIp=DISABLED}" \
  --query 'tasks[0].taskArn' --output text
```

Read the result in the log group once the task has stopped:

```zsh
aws logs tail /acme-demo/db-init --since 15m
```

You should see `reachable:` for the four data stores, then `database exists:` for each of the five
databases.

### The services

`apply` doesn't wait for the services to start. A Spring Boot service takes a minute or two to
pass its health check. Wait until all eight services (seven apps and the collector) run their
desired count; identity should show 2:

```zsh
aws ecs describe-services --cluster acme-demo \
  --services identity customer notification product shopping-cart customer-frontend admin-frontend adot-collector \
  --query 'services[].[serviceName, runningCount, desiredCount]' --output text
```

A service stuck below its desired count usually has a task that stops at startup. Read its log
group, `/acme-demo/<service>`, and the stopped task's reason in `aws ecs describe-tasks`.

Then check the edge:

```zsh
eval "$(terraform output -json urls | jq -r 'to_entries[] | "\(.key)=\(.value)"')"
curl -s "$customer/api/health"          # the customer frontend
curl -s "$admin/api/health"             # the admin frontend
curl -s "$api/api/v1/products" | head -c 200   # the product service, through the API host
curl -s -o /dev/null -w '%{http_code}\n' "$api/actuator/health"   # 404: /actuator isn't routed
```

By hand in the browser, at the `www.` URL: register, open the verification email, sign in, browse
products, and add an item to the cart.

**Until Debezium is deployed (PIN-543), only browsing works end to end.** Identity and the cart
publish their events through the outbox table, and nothing reads the table without a Debezium
connector: no verification email is sent, and the customer and cart read models stay empty. So
registering, verifying, and the signed-in cart can't be checked yet. The health checks, the
routing, and the metrics, logs and traces below don't depend on it.

A token from either identity task must be accepted by the other, and a redeploy must keep users
signed in, because both tasks sign with the key in `acme-demo/jwt-signing`. This needs a signed-in
customer, so it waits for PIN-543 too. Sign in, then:

```zsh
aws ecs update-service --cluster acme-demo --service identity --force-new-deployment
```

Once the new tasks are healthy, reload the page: you should still be signed in.

Metrics, logs and traces:

- Managed Grafana, with the Prometheus data source set up as in the foundation runbook: `up`
  should be 1 for the `*-service` jobs. Identity runs two tasks and the collector scrapes one at
  random each time, so identity's `rate()` and `increase()` graphs are unreliable here.
- CloudWatch Logs: the `/acme-demo/<service>` log groups.
- X-Ray: traces for the services, after some traffic.

## Destroy

```zsh
terraform destroy
```

Check that nothing is left. Both commands should return nothing for this stack. The first one
leaves out task definitions, which stay behind as inactive revisions (below). The second includes
secrets scheduled for deletion, the ones that would block the next `apply`:

```zsh
aws resourcegroupstaggingapi get-resources --tag-filters Key=Stack,Values=demo \
  --query 'ResourceTagMappingList[?!contains(ResourceARN, `":task-definition/"`)].ResourceARN'
aws secretsmanager list-secrets --include-planned-deletion \
  --filters Key=name,Values=acme-demo/postgres,acme-demo/documentdb,acme-demo/jwt-signing,acme-demo/test-api-key,acme-demo/service-tokens \
  --query 'SecretList[].Name'
```

The secrets are deleted at once, so a new `terraform apply` right after a `destroy` reuses the
same names. ECS keeps the task definitions as inactive revisions; they cost nothing and the next
`apply` registers new ones.
