## 2026-05-19 pin-92-token-refresh (branch)

- **AuthenticationController.kt:226** — TOKEN_REUSE_DETECTED error code leaks reuse-vs-expiry distinction
  - **Severity:** medium
  - **Reason for rejection:** The user-story spec (AC-0003-12-07, "Security Alert on Reuse") explicitly requires `TOKEN_REUSE_DETECTED` as a distinct code so client-side analytics / future security UX can surface the reuse signal. Frontend interceptor treats both `TOKEN_EXPIRED` and `TOKEN_REUSE_DETECTED` with identical cleanup today; the distinction is server-side observability. Info-leak risk is bounded: only an attacker already holding a stolen token can probe. Misleading docstring fixed in commit `f8709c2`.
  - **Reviewed by:** opus

- **RefreshTokensUseCase.kt:119** — Reuse check fires before user-existence check; deleted user + stale token publishes events referencing a non-existent user
  - **Severity:** medium
  - **Reason for rejection:** User deletion isn't shipped in this codebase yet — the edge case is unreachable in practice. `findByUserId` on a non-existent user returns empty, so the all-session sweep is a no-op. Revisit reuse-event semantics when user-deletion UX is built (US-TBD).
  - **Reviewed by:** opus

- **TokenReuseDetected.kt:62** — `UUID.fromString(aggregateId.removePrefix("sess_"))` assumes every sessionId starts with `sess_` and contains a UUID suffix
  - **Severity:** low
  - **Reason for rejection:** Identical pattern already shipped in `SessionInvalidated.kt` (and other Session-aggregate events) — the assumption is consistent across the event hierarchy and matches how `Session.create` mints IDs. Widening `DomainEvent.aggregateId` from UUID to String would touch the entire event hierarchy and is out of scope for PIN-92. If a future event type doesn't fit the UUID-suffix shape, the refactor becomes load-bearing and we should do it then.
  - **Reviewed by:** opus
